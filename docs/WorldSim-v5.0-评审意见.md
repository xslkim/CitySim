# WorldSim v5.0 方案评审意见

> 评审对象：`docs/WorldSim-最终方案.md`（产品重构版 v5.0，2026-09-28）
> 评审日期：2026-09-28

---

## 总体判断

方案在产品层面是成熟的：定位清晰、有所不为、"美术先行 + 体验门禁"的优先级判断正确；L0–L3 编剧边界和 append-only 事件流是两个关键且正确的架构决策。

主要风险不在"想得不对"，而在几个**核心机制还没有设计到可实现的深度**——记忆/信息传播模型、重要性评分、快照与分叉语义、成本量化模型。这些恰好是阶段 1~3 的成败点。建议不推翻方案，但在阶段 1 开工前补齐四份小型设计文档（见文末清单）。

---

## 一、做得对、值得保留的部分

1. **阶段排序正确**：先证明"看它本身有吸引力"（阶段 0）再投入内核，比前版"内核优先"更符合这个产品最大的不确定性。
2. **三核心同等重要 + 体验验收代替商业指标**：避免用留存/付费过早扭曲产品判断。
3. **L0–L3 编剧边界**（§9.3）：防止"编剧"滑向操纵角色心智，是"活着不是演着"的制度化保障。
4. **事件溯源 + 回放不重算 LLM**（§9.1）：因果可查、成本可控、回放一致，一石三鸟。
5. **动态认知分层**（§2.2）：40 人可持续运行的成本控制核心。
6. **美术质量门禁五问**（§8.3）：可操作、可执行，"风格锁定先于批量生产"能避免大量返工。
7. **成本自动降频/停钟**（§14.1）：方向正确（不足见缺口 4）。

---

## 二、关键缺口（按优先级排序）

### 1. 旗舰玩法"涟漪 / 信息失真"没有机制设计 —— 最大缺口

- §4.4 把涟漪视图定义为"最有辨识度的主玩法"；§2.2 升格触发依赖"持有正在传播的信息"；§2.3 依赖"知道的事、相信的事和真正的事不必一致"。
- 但全文没有**信息模型**：信息如何表示、角色"决定告诉谁"如何发生、失真如何产生与控制、系统如何追踪一条信息的完整传播链。
- 没有它，涟漪视图无法落地，升格触发器也无法实现，§4.4 就是一张画不出来的饼。
- **建议**：补《信息与记忆模型》设计：信息对象（内容、来源、版本、置信度、失真规则）、分享决策（由关系/动机/场合驱动）、传播链记录（复用事件 schema 的 `caused_by` / `payload`）。

### 2. "高重要性事件"是全家桶依赖，但没有定义

- 升格降格（§2.2）、自动降速拉近镜头（§3.3）、跟随提示（§4.2）、"单个重要事件成本"统计（§14.1）全部以"重要性"为前提，但全文没有评分模型。
- **建议**：阶段 1 先用纯规则版重要性评分（参与人数、是否涉及被跟随角色、关系变化幅度、事件稀有度、资源 stakes），并记录评分分布供后续调参。

### 3. 创世设计（初始条件）缺失

- 涌现式叙事的质量高度依赖初始条件：40 人的初始关系图、秘密分布、信息不对等、预置的未解目标与冲突（"故事种子"）。方案只有六个多样性维度（§2.3），没有任何创世交付物。
- **建议**：阶段 1/2 增加《创世文档》交付物：角色小传、初始关系矩阵、信息分布表、N 个预置未解冲突。

### 4. 成本只有相对报警，没有绝对预算

- §14.1 的 1.5× / 2× 是相对"基线"的，但**基线未定义**；没有每模拟日预算、单次对话/反思的 token 上限。
- §3.3 作者可 4× 与"跳到下一个时段"：快进意味着 LLM 成本同倍放大，方案完全未提这笔账。
- 阶段 1 要连续跑 72 小时、阶段 3 要连续跑 14 天（§11）——验收前必须先给出成本上限，否则验收本身可能因成本不可行。
- §10.2 玩家可建私有分叉、可投放事件：这部分算力**谁付费、限额多少**，完全未提。
- **建议**：定义"每模拟日 LLM 调用预算"并作为阶段 1 门禁之一；为每个认知层定调用频率与 token 上限；明确快进/分叉的放大系数与配额。

### 5. 快照 / 分叉 / 故障恢复的工程语义不足

- §9.4 只有四条 bullet，但这是全文工程难度最高的部分。未定义：快照内容（是否包含各 Agent 记忆库、关系图、目标栈）、快照频率、故障后恢复流程（从哪个快照 + 重放哪些事件）、事件 schema 版本化（一个要跑数月的世界**必然**会改 schema）。
- **建议**：阶段 1 交付物中明确"快照规格 + 恢复演练"——kill 掉进程后能从快照 + 事件流恢复到一致状态，才算通过。

### 6. 调度与并发因果未定义

- 没有 tick 模型（连续时间还是离散步？）、没有共享空间/多事件并发仲裁（两个角色同时想进入同一场对话？对话中一方被更高优先级事件拉走？）、没有说明事件日志是否单写者。
- **建议**：明确基本约定，例如"每世界单写者事件日志 + 离散 tick + `caused_by` 单源因果链"。

### 7. LOD 升降格缺少防抖与容量仲裁

- §2.2 升格触发器很多，但没有冷却/滞回机制：边界角色会在聚焦层与活跃层之间振荡，造成记忆写入断档和成本尖峰。
- 聚焦层上限 6~8 人，若 10 人同时达标，谁进谁出？没有优先级规则。
- **建议**：升格评分 + 优先级队列 + 最短驻留时间/降格冷却。

### 8. 只有视觉质量门禁，没有文本/叙事质量门禁

- LLM 台词会迅速趋同于"礼貌的平庸"，这是此类产品的已知死亡方式。§8.3 五问全部是视觉；对话与叙事没有对应门禁。
- **建议**：增加文本门禁：盲测猜说话人（遮住名字能否辨认是谁说的）、陈词滥调检测清单、每角色一张 voice card；纳入阶段 2 验收。

### 9. 玩家输入的安全审核链路缺失

- §4.5 可投放的社交事件包含"匿名消息"；§10.2 玩家在权限允许时可投放事件、可建分叉。玩家输入会进入世界、被 LLM 加工后**公开展示**——这是一条完整的内容安全攻击面。
- §14.2 只提了 AI 生成内容标识，没有输入审核、投放频率限制、LLM 输出安全过滤（角色冲突剧情完全可能产出骚扰/成人/暴力内容）。
- 事件 schema 里的 `safety_state` 字段是好的种子，但没有配套流程。
- **建议**：阶段 4 触发前定义完整链路：输入审核 → 投放配额 → 输出过滤 → `safety_state` 流转与人工复审。

### 10. 一致性审计没有指标与阈值

- §9.2 提到"系统校验"、§11 阶段 1 交付"一致性审计"，但审什么、什么算失败，全文未定义。
- **建议指标**：事实矛盾率（位置/余额/日程）、对话引用不存在记忆的比例、日程违规率；审计失败率超阈值自动暂停模拟时钟（与 §3.1 衔接）。

### 11. 工期风险：阶段 0 与阶段 1 范围偏大

- 阶段 0（1~2 周）：3 套完整视觉方向，每套含三级人物、两种对话、三个时间版本、涟漪可视化、桌面+移动双端，外加一个含跟随/对话/时间带/涟漪的可点击原型和两块完整角色设定板——对小团队极易超时。
- 阶段 1（2~4 周）：从零到"完整决策闭环 + 事件流 + 快照回放 + 审计 + 连续 72 小时无故障"，同样紧张。
- **建议**：阶段 0 收敛为 2 套完整方向（或明确第 2/3 套允许降低完成度），原型交互砍到"看 / 跟随 / 时间带"三个；阶段 1 把"一致性审计"限定为缺口 10 的最小指标集。

### 12. 各阶段没有退出 / 终止条件

- §11 只写了"通过验收进入下一阶段"，没写"不通过怎么办"。没有 kill criteria 的阶段门禁，实际执行时会变成"差不多就进下一阶段"。
- **建议**：每阶段补一条终止/回炉标准。例：阶段 1 若无法在预算内 72 小时连续运行且一致性达标，则回炉认知架构，不带病进入阶段 2。

### 13. 公共世界 1× 流速的故事密度未被论证

- 1× 意味着一个模拟日 = 一个真实日；发薪、截止日级别的故事弧以**真实周**计。"离开 4 小时有有意义变化"是作者世界（可变速）的验收标准，公共世界玩家"单次观看能看到多少故事"没有任何指标。
- **建议**：阶段 2 起埋点"每观众分钟可讲述事件数"，用数据决定公共世界流速与事件密度旋钮；把"公共世界是否应略快于 1×（如 1.5~2×）"记录为开放问题。

## 三、次要问题与待澄清点

1. **人群重叠**：公司 16 人与公寓 24 人是否重叠（公司角色住公寓吗）？影响空间与关系拓扑设计。
2. **经济系统规则空白**：发薪/账单/股价类事件（§4.5）需要收入、房租、支出的基本规则，否则"经济事件"是空中楼阁。阶段 2 前补一页纸即可。
3. **多人对话语义**：§9.1 的记忆投影只举了两人对话的例子，3 人以上对话的可见度与投影规则未提。
4. **陌生人测试协议**：阶段 0 和 §12.2 依赖"3~5 名陌生人无讲解测试"，但没写招募渠道与协议。建议最小协议：无讲解观察 10 分钟 + 事后三问（你在看谁 / 为什么 / 想知道接下来什么）。
5. **玩家互相可见性**：钉住列表、笔记是否社交化？建议现在就在阶段 4 标注为"有意暂不设计"，避免届时摇摆。
6. **最小技术选型清单**：事件存储、前端渲染技术、模型供应商与降级策略——产品方案可以不含，但阶段 0/1 开工前需要单独一页。
7. **冷启动入口**：不做每日切片生产线是对的，但陌生玩家进入时需要一个"今天发生了什么"的轻量摘要入口，建议记录为开放问题。

## 五、结论

**方案值得执行，不需要推翻。** 优先级最高的三件事：

1. 把"涟漪"从卖点变成机制设计（缺口 1、2、3）；
2. 把成本从相对报警变成绝对预算（缺口 4）；
3. 给阶段 1 补上快照恢复规格与阶段终止条件（缺口 5、12）。

这三类补齐后，§11 的阶段路线是可以信任的。
